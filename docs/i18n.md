# Language support and migration plan

Language support is established before expanding the TUI controls. The existing
interface mixed Chinese dashboard labels with English Bubbles help, Huh forms
and CLI feedback. Keeping new strings in individual components would multiply
the work needed for every later language or interaction change.

## Configuration and interaction

Language shares the existing `config.yaml` with theme preferences:

```yaml
language: en
theme:
  name: tokyo-night
  mode: auto
```

Supported preferences are `zh-CN`, `en` and `auto`. An omitted or empty value
also means automatic selection. An explicit supported language wins over the
environment. Automatic selection follows `LC_ALL`, then `LC_MESSAGES`, then
`LANG`; common regional and encoding suffixes such as `en_US.UTF-8` are
accepted. An unset or unsupported system locale, including `C`, falls back to
Simplified Chinese. An invalid explicit preference falls back with a TUI
warning. A wrong-shaped optional language field cannot block core commands.

Settings → Language provides System default, 简体中文 and English. Arrow keys
and mouse hover preview the language immediately; `Enter` or an option click
saves it, while `Esc`, changing pages or quitting restores the saved language.
Previewing performs no configuration write. Saving uses the existing state lock
and reloads the latest configuration, preserving theme and kernel changes.
Resetting appearance does not reset the separate language preference. An
already-open subscription manager reads external language changes on reopen.

Configuration names, theme IDs, commands, shortcuts and machine-readable
output retain their stable values. Language selection never changes a command's
behavior or shell output. Theme export remains YAML only on stdout.

## Implementation choices

`internal/i18n` holds paired Chinese and English catalogs with stable semantic
keys. UI models own their resolved `Locale` and pass it to shared selectors and
dialogs. `Text(locale, key, args...)` provides formatting and a Chinese fallback;
an unknown key stays visible as the key so a missing message is diagnosable.
There is no mutable global translator. Runtime preview is local to its model,
which keeps cancellation predictable and avoids cross-model data races.

The current scope uses the standard library rather than a new localization
dependency. Two languages and simple count messages do not yet need a message
compiler, ICU syntax or a separate catalog loader. Catalog tests require both
translations and matching argument positions/types. If later languages need
plural or gender rules, evaluate a library against those concrete requirements
without changing stable message keys or the model's locale ownership.

When adding UI text:

- Add a semantic key with both translations; reuse shared messages for common
  actions. Keep values supplied by users and services outside translated keys.
- Use complete messages rather than joining translated sentence fragments.
  Prefer indexed `fmt` placeholders if a translation must reorder arguments.
- Assign status and focus styles from state rather than interpreting translated
  words. Derive mouse geometry from the rendered labels; English and Chinese
  have different cell widths.
- Keep library navigation, validation and list filtering. Override their public
  presentation hooks or wrap only the needed text; do not fork Bubbles/Huh to
  translate their internals.

## Priorities and remaining scope

The first migration covers the dashboard and appearance/language controls,
shared Dropdown/SelectModal/Modal messages, and the subscription manager's own
controls and profile forms. The theme import success response follows the same
preference. This puts a reusable language boundary in place before adding more
UI components.

Existing CLI help, kernel pickers, CLI operation-result renderers and domain or
third-party error details are not comprehensively translated in this stage.
They can still appear in English or their original language inside a localized
TUI. Do not import presentation catalogs into kernel, download or subscription
business logic merely to translate errors.

Next, migrate the remaining presentation helpers and CLI descriptions one
module at a time. Where a domain error needs a translated explanation, use its
existing typed error/result or add a stable error code at the presentation
boundary; retain the original detail for diagnostics. Keep JSON keys, enum
values, configuration fields and executable shell statements unchanged.
Broaden languages only after the Chinese/English keyboard, mouse, wrapping,
resize and preview flows remain covered. Whole-project i18n is therefore an
ongoing migration, not a completed checkbox for every existing output string.
